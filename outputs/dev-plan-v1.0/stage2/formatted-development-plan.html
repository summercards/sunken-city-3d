执行摘要

本计划的目标是在现有 Three.js 水下场景与交互原型基础上，交付首个可连续体验的 20 分钟玩法 Demo；当前基线已具备三个可交互区域、建筑建设/收取/升级、角色与船只航行、场景动态表现及两份回归测试，但仍缺少首局任务链、多资源库存、打捞、船只成长、区域解锁与持久化。

当前基线：保留现有视觉资产和场景架构，优先补齐玩法垂直切片，避免以继续增加装饰模型替代核心流程建设。

四个里程碑：

  • P0：把现有能力串成从进入、建设、收取、升级到航行的最小闭环。
  • P1：补齐木料、旧零件、打捞、码头、船只升级与区域解锁，完成 20 分钟 Demo。
  • P2：增加居民、区域复兴、发现事件和生活反馈，让世界随建设持续恢复。
  • P3：完成存档、性能、兼容性、配置化和自动化测试，形成长期维护基础。

交付门槛：新玩家 30 秒内理解目标，3 分钟内完成第一次建设，12 分钟内完成家园升级，20 分钟内完成船只升级并抵达新区域；全程无运行时错误，现有回归测试继续通过，且新增内容不破坏场景艺术、UI 锚点与窄屏体验。

1. 计划概述

本章说明项目定位、首个 Demo 的核心目标，以及用于判断是否完成交付的体验结果。

1.1 项目定位

《淹没之城：晴空水巷》是一款治愈系水上家园建造与轻度资源经营游戏。

玩家从一座被海水淹没的城市废墟出发，在屋顶、码头和沉没街区之间往返：

  1. 发现可修复的建筑与种植空间。
  2. 修复第一块屋顶或种植床。
  3. 观察植物、设施和生活细节逐步生长。
  4. 收集海贝、木料、旧零件等资源。
  5. 升级太阳能木屋和船只。
  6. 驶向新的沉没街区，看到下一阶段的建设目标。

1.2 首个 Demo 的核心目标

首个 Demo 不追求完整游戏内容，而是验证一条连续、可理解、可重复体验的 20 分钟核心流程：

TEXT
起始木屋
  → 发现可建设地点
  → 修复第一块种植床
  → 种植并等待生长
  → 收获海贝或基础资源
  → 升级太阳能木屋
  → 收集船只升级材料
  → 在码头升级木船
  → 驶向远处沉没街区
  → 看到下一座待建设屋顶

1.3 Demo 交付判断

首个 20 分钟 Demo 至少应满足以下体验结果：

  • ☐玩家在首次进入后 30 秒内知道自己可以点击建筑、船只或角色。
  • ☐玩家在前 3 分钟内完成一次明确的建设行为。
  • ☐玩家能观察到建设过程中的阶段性变化，而不是只看到数字变化。
  • ☐玩家在 7 分钟左右完成一次资源收取或资源分配。
  • ☐玩家在 12 分钟左右完成太阳能木屋或家园中心升级。
  • ☐玩家在 20 分钟以内完成一次船只升级并驶向新的区域。
  • ☐Demo 结束时，玩家对“下一座屋顶可以建设成什么”产生明确期待。
  • ☐核心流程不依赖战斗、复杂菜单或长时间阅读。

2.2 非目标

以下内容不纳入首个 20 分钟 Demo 的交付范围：

  • ☐不实现完整自由放置、旋转和拆除式家园建造。
  • ☐不实现战斗、敌人、生命值、武器或失败条件。
  • ☐不实现多人联机、社交关系或玩家间交易。
  • ☐不实现开放世界自由驾驶和实时船只碰撞。
  • ☐不实现完整天气、潮汐、昼夜和季节系统。
  • ☐不实现复杂居民职业、对话树和任务编辑器。
  • ☐不实现完整生产链、复杂配方和大规模仓储管理。
  • ☐不在首个 Demo 中扩展大量新区域。
  • ☐不以继续增加装饰模型作为主要开发目标。
  • ☐不替换现有 Three.js 场景架构。

2.3 设计取舍原则

  1. 先保证流程完整，再增加内容数量。
  2. 先让资源和升级形成闭环，再扩展资源种类。
  3. 先让船只升级有明确作用，再增加复杂航海玩法。
  4. 先保证玩家看懂目标，再优化数值深度。
  5. 任何新增系统都必须服务于首个 20 分钟体验。

3.5 基线结论

当前工程适合继续采用“保留现有视觉场景，补齐玩法垂直切片”的路线。

当前最重要的缺口不是场景数量，而是以下四项：

  1. 现有三个建设点尚未形成明确的 A-D 功能分工。
  2. 海贝之外缺少支撑修缮和船只升级的基础资源。
  3. 当前航行已有表现，但船只升级尚未成为真正的成长系统。
  4. 缺少一条由任务、目标提示和解锁条件串联起来的首局流程。

P0 不要求完成全部经济系统，但必须保证：

TEXT

  → 完成一次建设
  → 看到视觉变化
  → 获得资源
  → 完成一次家园升级
  → 选择目的地

6. P1：资源经营与船只成长

6.1 P1 目标

P1 是首个 20 分钟 Demo 的核心交付里程碑。

P1 要把当前“海贝加建筑升级”的原型，扩展为一个最小但完整的双层资源循环：

TEXT
建设或种植
  → 产生海贝或基础资源
  → 收取并进入库存
  → 消耗资源修缮或升级
  → 解锁更高价值的建设和航行

6.2 P1 功能职责

P1 依赖 P0 的以下结果：

  • ☐建设状态可被可靠读取和更新。
  • ☐角色和船只状态不会因跨区域操作失步。
  • ☐建筑操作点的收取、升级和不可用状态保持兼容。

6.5 P1 验收标准

  • ☐海贝、木料和旧零件具有独立的库存显示或可访问状态。
  • ☐资源不足时显示明确的缺口，而不是无响应。
  • ☐至少一个建设行为同时消耗海贝和基础资源。
  • ☐玩家可以在 5 分钟内接触到一次打捞或材料获取行为。
  • ☐打捞结果可以进入库存，并能用于后续升级。
  • ☐船只至少有两个可识别等级。
  • ☐船只升级会带来至少一项可见或可感知变化：模型变化、航行速度变化、航线/区域解锁、货舱/资源能力变化，至少满足一项。
  • ☐玩家可以在 20 分钟内完成一次船只升级。
  • ☐船只升级后的远航可以抵达新区域或触发明确的 Demo 终点。
  • ☐首局不需要玩家依赖隐藏规则或源码知识。
  • ☐P0 与现有 UI、场景回归测试全部通过。

7. P2：世界反馈与生活感

7.1 P2 目标

P2 不再以“能不能完成首局”为核心，而是增强“修复后世界真的活起来了”的反馈。

11. 首个 20 分钟体验设计

11.1 0–3 分钟：理解世界并完成第一项建设

玩家目标：

  • ☐看到晴空水巷和起始木屋。
  • ☐发现附近的可建设点。
  • ☐点击建筑或角色进入行动。
  • ☐通过一次航行或短距离移动抵达建设位置。
  • ☐消耗初始资源完成第一阶段建设。

必须提供的反馈：

  • ☐当前任务明确。
  • ☐建筑热点可见但不遮挡主要画面。
  • ☐建设过程有进度变化。
  • ☐干燥土壤变湿。
  • ☐修缮构件逐步出现。
  • ☐幼苗在固定位置萌发。

11.2 3–7 分钟：观察生长并完成第一次收获

玩家目标：

  • ☐观察植物从幼苗到成株。
  • ☐返回或切换到可收取建筑。
  • ☐收取第一批海贝或基础资源。
  • ☐明白资源不是只会自动增加，也需要主动收取。

必须提供的反馈：

  • ☐收取优先于升级。
  • ☐收取后操作点位置不变。
  • ☐顶部资源数字有轻量反馈。
  • ☐资源不足时显示缺口。
  • ☐建设中的建筑显示忙碌状态。

11.3 7–12 分钟：升级家园中心

玩家目标：

  • ☐使用海贝与基础资源升级太阳能木屋。
  • ☐看到木屋、码头、灯光、植物或生活物件发生变化。
  • ☐获得下一步“修缮船只”或“收集旧零件”的目标。

必须提供的反馈：

  • ☐木屋升级不能只修改等级数字。
  • ☐至少出现一种新的生活细节。
  • ☐升级后开放新的建设或资源入口。
  • ☐玩家能够理解家园升级与船只升级之间的关系。

11.4 12–20 分钟：升级船只并驶向下一处区域

玩家目标：

  • ☐通过打捞或建设获得旧零件。
  • ☐在码头打开船只升级入口。
  • ☐消耗资源完成船只升级。
  • ☐看到船只外形、灯光、航行速度或航线能力变化。
  • ☐驶向新的沉没区域。
  • ☐抵达后看到下一处待建设目标。

必须提供的反馈：

  • ☐船只升级有明确成本。
  • ☐船只升级有明确收益。
  • ☐未升级时目标区域不可用或提示原因。
  • ☐升级后目的地选择中出现新区域。
  • ☐Demo 结束时保留下一阶段期待，不强迫玩家继续完成所有内容。

13. 风险与降级策略

风险可能表现预防措施降级策略
P0 范围膨胀还未完成闭环就开始增加新区域和装饰以 20 分钟关键路径作为唯一验收主线暂停新内容，只保留现有三个区域
多资源系统过重玩家需要管理过多资源，节奏变慢首个 Demo 只使用海贝、木料、旧零件暂时隐藏食物和特殊材料
船只升级不明显玩家完成升级后看不出变化预先定义至少一种模型或航线变化先采用明显颜色、灯光或船帆变化
航行等待过长玩家在航线上无事可做控制航行时间，保证沿途有视觉发现采用快速航行或跳过航行动画
UI 遮挡场景任务、资源和热点互相遮挡保持上下文显示，避免常驻大面板只显示当前目标和必要资源
状态机失步角色、船只、相机和任务状态不一致所有状态转换统一经过状态机失败时回退到最近安全状态
场景艺术与玩法脱节数字升级了但模型没有变化使用统一的场景表现接口先启用简单灯光、植物或构件变化
随机动画影响测试回归截图和状态断言不稳定测试中冻结时间和随机数使用固定测试种子与受控时钟
绘制调用持续增加低端设备掉帧静态对象按材质合批，动画对象独立保留降低远景、阴影、粒子和动态生物数量
WebGL 能力不足黑屏、Shader 失败或帧率过低启动时检查能力并建立档位使用低像素比、关闭阴影和复杂 Shader
数值节奏失衡玩家太快完成或长时间等待记录关键节点时间通过配置快速调整成本、产出和冷却
存档字段变化版本更新后旧存档无法读取存档增加版本号和迁移入口无法迁移时安全重置并给出说明
引导过度玩家被提示和任务打断只在首次出现时展示提示允许关闭非关键提示

15. Definition of Done

15.1 功能完成

  • ☐玩家可以从新游戏开始完成一条连续的 20 分钟体验。
  • ☐玩家可以完成至少一次建设。
  • ☐玩家可以看到建设过程和完成后的场景变化。
  • ☐玩家可以主动收取资源。
  • ☐玩家可以完成一次家园或木屋升级。
  • ☐玩家可以获取木料或旧零件。
  • ☐玩家可以完成一次船只升级。
  • ☐船只升级后至少有一项明确收益。
  • ☐玩家可以前往一个新区域。
  • ☐新区域抵达后有明确的下一阶段目标。

15.2 状态一致性

  • ☐资源扣除只发生一次。
  • ☐资源增加只发生一次。
  • ☐建设中不能重复开始同一任务。
  • ☐角色不能同时处于登船和下船状态。
  • ☐船只航行中不能重复触发目的地选择。
  • ☐区域解锁状态与目的地菜单一致。
  • ☐任务状态与实际建设状态一致。
  • ☐场景视觉状态与玩法状态一致。
  • ☐错误操作不会使玩家永久卡死。
  • ☐失败状态可以回退到最近安全状态。

15.3 视觉与交互

  • ☐保持当前水下手绘水彩视觉方向。
  • ☐保持建筑、植物、修缮构件的阶段性变化。
  • ☐建筑热点和悬停卡片继续随相机正确投影。
  • ☐收取、升级、建设和船只升级具有清晰反馈。
  • ☐不恢复大面积常驻底部工具栏。
  • ☐任务提示不遮挡核心场景。
  • ☐390px 窄屏无横向滚动。
  • ☐prefers-reduced-motion 下仍能完成核心操作。
  • ☐关键交互具备键盘或焦点替代路径。

15.4 测试完成

  • ☐tests/ui-regression.cjs 继续通过。
  • ☐tests/scene-art-regression.cjs 继续通过。
  • ☐首局关键路径测试通过。
  • ☐资源状态测试通过。
  • ☐船只升级和区域解锁测试通过。
  • ☐无 JavaScript 运行时错误。
  • ☐无明显 Shader 编译错误。
  • ☐关键截图回归通过。
  • ☐性能基线已记录。
  • ☐至少一种低端设备降级方案已验证。

15.5 Demo 交付标准

  • ☐新玩家无需源码知识或人工讲解即可完成首个目标。
  • ☐前 3 分钟内可以完成第一次有效建设。
  • ☐前 12 分钟内可以完成一次家园升级。
  • ☐20 分钟内可以完成一次船只升级并驶向新区域。
