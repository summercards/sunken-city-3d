## 5. 0.1 最小顺序与验收决定

1. **先确定验收入口，再考虑写代码。** 如果 0.1 要在同一局提供三态并保留其它功能，建议用 **B** 做集成/发行验收入口，**A 只留作可编辑的陆地白盒**。当前 F5 是 A，这是首要产品差距，不是缺三套引擎。未来经批准才调整入口/发行配置（`project.godot`、`profiles/legacy_main.cfg` 和 runner 的入口检查）；不得只换场景地址漏掉三个 Autoload，不在主工程装 override 试真档。冻结当前 TSCN 和稳定 ID；若要求保持 A 为默认，则需明确另外提供同一局三态的正式入口，不把 A 的陆地绿灯算作 0.1 放行。
2. **用一条现有生产动线验证，不先上新系统。** 选家园低矮泊位和现有安全上岸段：走路/停住→到泊位→上船/划离→不同角度碰岸后脱离→停船下潜→水平/升降/障碍→返同一船→回泊位上岸。同时验收取消、抢输入、过场重入、冷却、相机唯一及失败保持原位。先用同一输入动作和已有命令，不另写 `InputContext`、统一 motor 或新 FSM。重复执行顺序和短/长按各测一轮。
3. **只做两个已定位方向的最小补齐。** 优先复现泊位判据不一致，确认后共用查询；再针对选定动线有实证的墙/坡/走面不一致或镜头穿墙补局部场景/查询。不把船壳实体化当成默认前置；若岸线代理达到“不穿实体且可脱困”的可玩验收，就保留。扩大到新物件时，编辑器拖动可玩 prefab 根，保存重开，模型、碰撞及站位一起走；缩放/改尺寸要同时校尺，不承诺任意导入件零配置。只处理受影响的设施，不重排全图。
4. **按影响面逐项放行。** 先走独立物理与输入专项，再做 B 原生窗口三态连续实玩和失败注入，最后按上表有影响才回归经营和存档夹具；A 应继续独立可跑。验收看的不是“新类多少”，而是单一控制主体、连续的移动与镜头、拒绝不遗留状态、场景能编辑、原功能没丢。若后续授权实施，既有 FeatureID 下只追加实际变化与证据、更新开发记录；涉及新带入/手摆才同步位置台账，运行契约 sync/无参检查，不以未知资产哈希批量刷新消红。
