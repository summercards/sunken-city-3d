# 2026-10-31 建造系统性能审计与吸附求解优化

关联 SEA-BUILDING-R24（新增）。本轮不改数值、不改玩法、不改存档格式，只做结构层面的性能加固。

## 结论先放

**帧内热路径是健康的**，但发现并修复了一个会随建筑规模爆炸的缺陷：拖板预览的吸附求解是 O(n³)，45 块板时单次 163 ms —— 玩家铺一个正常大小的家，鼠标一移就卡死。

修复后 45 块板 **2.2 ms（74 倍）**，且 1620 条基准输出逐行一致。

## 一、实测：谁在花时间

50 实例（25 块板 + 二层结构 + 摆件）的真实帧成本：

| 路径 | 耗时 | 触发频率 | 判定 |
|---|---|---|---|
| `update_preview`（鼠标移动） | **0.198 ms** | 每帧 | 健康，占 60fps 预算 1.2% |
| `service.query()` 深拷贝 | 0.044 ms | 多处 | 健康 |
| `Surfaces.faces` 重建三维走面 | 0.081 ms | 布局变化 | 健康 |
| `walk_rects` 重建走面 | 1.354 ms | 布局变化 | 可接受 |
| `building_world.sync` 全投影 | 2.191 ms | 布局变化 | 可接受 |
| `validate_snapshot` 读档校验 | 3.828 ms | 读档一次 | 可接受 |
| 单次 `begin` | 1.428 ms | 建造一次 | 可接受 |

**只有 `update_preview` 在帧内循环里**，其余都是离散事件。这条边界是清楚的。

## 二、修复：吸附求解的立方复杂度

### 症状曲线（修复前）

| 板数 | `snap_foundation` |
|---|---|
| 5 | 1.67 ms |
| 12 | 8.91 ms |
| 21 | 29.92 ms |
| 32 | 76.63 ms |
| 45 | **163.49 ms** |

板数涨 9 倍，耗时涨 98 倍。45 块板 = 玩家一个 7×7 的家，完全正常。

### 根因

原实现每生成一个候选，都要重扫全部承载面做三件事：

```gdscript
for tile in surfaces:                    # O(n)
    for side in 4:                       # 4
        for other in surfaces:           # O(n) —— 只为收集齐平坐标
            for raw in [...]:            # 2
                if platform_contact(rect, rows) < JOIN_MIN:   # 内部又 O(n)，且重建 support_tiles
                if overlaps_any(rect, surfaces):              # 内部又 O(n)
```

外层 O(n)、中层为收集坐标又 O(n)、每个候选的接触与重叠检查再各 O(n)，叠加成 O(n³)。雪上加霜的是 `platform_contact` 内部每次调用都 `support_tiles(rows)` 重建一遍数组。

### 改法

三处结构性改动，都不改语义：

1. **`contact_against(rect, surfaces)`** —— 接受已物化的承载面数组，不再重建 `support_tiles`。
2. **`build_index` / `neighbours`** —— 稀疏桶空间索引（4 米一格），候选的接触与重叠只查自己所在邻域，不再全表扫描。
3. **`unique_slide_positions`** —— 沿边滑动位置只取决于角点集合与候选边长，与"贴哪条边"无关，因此竖直/水平两个方向各预计算一次，复用到所有边。
4. **提前距离剪枝** —— 结果是按"光标到候选矩形的距离"排序取最近，所以距离一旦不可能更优就直接丢弃，不进入接触/重叠这两步。

### 修复后

| 板数 | 修复前 | 修复后 | 提升 |
|---|---|---|---|
| 5 | 1.67 ms | 0.25 ms | 6.7× |
| 12 | 8.91 ms | 0.77 ms | 11.6× |
| 21 | 29.92 ms | 1.32 ms | 22.7× |
| 32 | 76.63 ms | 1.77 ms | 43.3× |
| 45 | 163.49 ms | **2.21 ms** | **74×** |

曲线从立方降到近线性（5→45 板 9 倍，耗时 8.7 倍）。

## 三、等价性：这次优化一个解都没改

性能优化最怕「快了但顺手改了行为」。为此先存基准、再改代码、最后逐行比对。

基准覆盖 1–5 块板的五种布局 × 3 种候选（`raft_4x4` / `raft_2x4` / `deck`）× 3 种朝向 × 沿 x 与沿 z 两条扫描线，记录 `snap_foundation` 与自由水域版本的完整输出，共 **1620 条**。

第一次改完是**失败的**：312 行不同。原因是我把边集合改成了排序去重的集合，而原实现按「板顺序 → 每条边」遍历；当多个候选与光标等距时，先被记录的胜出，排序改变了这个顺序，于是同样的最优解变成了另一块板的位置。

改法：保留原始遍历顺序（把角点按 `[start, end, start, end, …]` 预存一份，复用于每一块板），只把「重复扫描全部承载面」换成「复用这份序列」。再测 —— **1620 条逐行完全一致**。

这条记在交付里，是因为它说明：等价性不能靠"看起来对"，必须逐字节比对。第一版优化在功能测试里很可能也是全绿的（两个解都合法），差异只体现在玩家看到板子偏移了 0.575 米。

## 四、门禁：`building-perf`

7 项，两个方向：

- **结果等价**：内置一份"参考实现"（就是修复前的形状，慢但正确），对 588 个样本点逐项比对。留一份参考实现的成本，小于「某天调性能顺手改了玩法没人发现」的成本。
- **耗时曲线**：45 块板必须 < 12 ms（单帧预算内），且 9→25 块板的增长倍数 < 12×。留了充足余量，适配较慢的机器，但退化回旧实现的 163 ms / 18× 会立刻失败。

**反向验证**：把旧实现临时注入，门禁两条立刻红（`45-board snap stays inside one 60fps budget slice (29.43 ms)`、`growth from 9 to 25 boards stays near linear (18.1x)`），而等价性断言仍绿 —— 同时证明了「门禁有效」和「两个实现结果一致」。恢复后 7 项 0 失败。

## 六、渲染侧：测不出结论，如实记录

用真实渲染器跑了空布局 / 13 板 / 25 板 / 25 板+12 摆件四档，帧时间**恒定 6.90 ms** —— 这是垂直同步在限速（≈145 fps），负载差异被 vsync 吃掉了，所以这批数字**不能用来判断大布局的渲染成本**。

能确定的只有节点数：每块 4×4 浮台预置体含 18 个 `MeshInstance3D`，25 块板 450 个。这些网格共用 4 套材质，理论上可以合批，但**未实测 100+ 板下的绘制调用数与帧时间**，不做任何无根据的承诺。

如果后续要给结论，需要：关闭 vsync、用 `RenderingServer.get_rendering_info()` 取绘制调用数，并在 100 / 200 板两档做压测。本轮未做。

## 八、下一步建议（性能方向）

1. **渲染压测**：关 vsync，取绘制调用数，测 100 / 200 板。这是目前唯一没有数据的维度。
2. **`walk_rects` 的 O(n²)**：如果玩家真能建到 100+ 板，2 ms → 6 ms 会开始有感觉。可以用与吸附求解相同的桶索引思路。
3. 其余（`query` 深拷贝、`faces`）都在健康区间，不值得动。

数值平衡（木料产出 vs 建造消耗）仍未改，等明确要求。
