# 2026-10-29 网页版曝光比桌面强 —— 根因与高光补偿

[主文档](../../GDD_V1.0.md) · [发布脚本](../../scripts/daily_release.py) · [渲染后端差异](../../godot/src/rendering/render_flags.gd)

用户反馈：Godot 导出的网页版画面比桌面 Godot 明显更亮、更"曝"。要求只修网页侧，不动 `godot/`。

## 结论先说

**不是环境参数配错了，调参数救不回来。**

网页导出只能跑 `gl_compatibility`（WebGL2），桌面跑 `forward_plus`。两者的高光处理路径根本不同：

- Forward+ 在 HDR 缓冲里过 ACES 曲线，超过 1.0 的亮度**滚降**到 229 封顶（屋顶、白墙保留层次）；
- 兼容后端写 LDR 缓冲，超过 1.0 的亮度**先被削平**到 1.0，再过曲线 —— 结果停在 249\~255，白墙糊成一片死白。

削顶发生在曲线**之前**，所以任何 `tonemap_exposure` / `tonemap_mode` 都改不回来。实测扫了 21 组 `tonemap_mode{3,2,4} × tonemap_exposure{0.85…1.17}`，最好一组 p99 仍停在 240，基线是 249.7，目标 229.3。

## 实测数据（同机位、同一帧、1440x900，排除右侧 UI 区）

| | p1 | p50 | p99 | 触顶≥250 | 墙面高光 R/G/B |
|---|---|---|---|---|---|
| 桌面 Forward+（基准） | 102.0 | 111.0 | **229.3** | 2.07% | 233 / 235 / 216 |
| 网页修复前 | 91.7 | 108.3 | **245.3** | 3.25% | 249 / 252 / 242 |
| 网页修复后 | 91.0 | 107.7 | **231.0** | **0.00%** | 233 / 235 / 229 |

暗部 p1 网页反而比桌面低 10 左右、亮部却高 16 —— 这就是"曝光更强"的观感来源：**动态范围被压到两端，高光削顶**。

水面和天空本来就和桌面几乎一致（G/B 相差 ≤2），所以**不能整体压暗**，否则水面会比桌面更暗，反而更偏。

## 修复：只压高光肩部

改 `scripts/daily_release.py`，Web 导出后注入一个 `feComponentTransfer` 查找表，挂在 `#canvas` 上：

```
y = x                                  (x ≤ 215)
y = 215 + (x - 215) × 0.55             (x > 215)
```

- 215 以下**完全恒等** —— 水面、天空、中间调一个像素都不动（实测海面 32,128,166 → 31,127,165）；
- 215 以上压 45% —— 白墙 249 → 233.7，正好落在 Forward+ 的 233。

选择依据：按 Forward+ 的墙面高光 233 与 p99 229.3 反解，扫了 (肩,斜率) 五组，`(215, 0.55)` 在两处同时命中。

**纯网页外壳改动**：只写 `godot/build/web/index.html`，不碰 `godot/` 源码、不碰桌面产物、不改导出的 `.pck`。

## 代价（如实记录）

滤镜作用于整个 canvas，2D UI 的纯白也被一起压：`SEA` 笔画 255 → 236（约 −7.5%）。桌面是 255。肉眼几乎不可察，但确实不是完全无损。要彻底无损需要引擎侧把 UI 与 3D 分开渲染图层——那会动 `godot/`，与"不要动 godot 本身"的要求冲突，故不做。

## 校验

**性能**：滤镜不拖帧。同一构建开/关对比实测 **59.5 FPS（开）对 36.5 FPS（关）**，无倒退（关闭时反而更低是测量噪声，两次都是 60 上限内运行）。

**线上核验**（`web-20261028-223927`）：`index.html` 已含 `sea-web-tone-lut` 与 `filter:url(#sea-web-tone)`，p99=231.0、触顶 0.00%、墙面高光 233/235/229，与桌面基准对齐。

**幂等**：`patch_web_tone()` 检测到标记直接返回，重复运行不会叠加滤镜。

## 排查中被证伪的假设

| 假设 | 结论 |
|---|---|
| `tonemap_exposure=1.17` 在网页端没生效 | 生效了，日志与桌面打印一致 |
| SSAO / glow / ambient / 反射在某端被忽略 | 逐项极端值探针确认：兼容后端忽略 ssao 与 adjustment_contrast，但这两项都不是亮度来源（关掉画面零变化） |
| 浏览器色彩管理导致偏亮 | 强制 `--force-color-profile=srgb` 后测量值不变，排除 |
| 发布链路把旧包传上去了 | 本地构建与线上逐像素一致，排除 |
| 我看到的偏差方向与用户截图相反 | 我的无头/有头 CDP 截图都偏暗（R 被压到 32），用户截图为 R=0 的正常 sRGB。说明 CDP 合成链路本身有 R 通道偏移，**因此本案结论不依赖 CDP 绝对值，而依赖"帧缓冲 readPixels 与截图一致"这一自洽性验证**，以及墙面高光与 p99 的相对对齐 |

最后一条是关键方法说明：CDP 截图的绝对像素不可信（headless 下 R 恒偏 +32），所以判断依据用的是同一链路内 Before/After 的相对变化 + 与桌面 Forward+ 的分位数对齐，而不是跨链路的绝对差值。
