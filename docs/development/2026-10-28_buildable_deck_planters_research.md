# 海上木板扩建与种植摆件：现状研究及建议方案

日期：2026-10-28。性质：代码与场景静态研究；尚未实现，不作为运行验收证据。

主功能：SEA-BUILD、SEA-FARM。协作功能：SEA-WORLD、SEA-MOVE、SEA-NAV、SEA-INTERACT、SEA-UI、SEA-INVENTORY、SEA-SAVE、SEA-ASSET。

## 1. 结论与玩家操作

可以复用当前木板美术，建立通用、可重复建造的木板预制体；种植箱作为独立摆件放在板上。已有种植规则继续使用，只扩展空间、实例登记和存档。

推荐首版流程：进入家园建造 → 选择木板 → 对齐现有平台边缘，显示半透明预览 → 确认并扣料 → 新木板可通行 → 选择种植箱 → 吸附到木板上的有效位置 → 确认并扣料 → 点击箱子使用现有种子气泡、浇水与收获。

建议首版限制为家园范围、同一高度、边相连、90度旋转；不允许角点接触算连通，不先开放任意海域孤立平台、多层或跨高度桥梁。具体网格尺寸、费用、材料来源和是否有工期尚未定案。这些是本次建议，不覆盖已生效的最小生活循环范围。

## 2. 已核对的工程事实

| 对象 | 当前实现 | 本需求的缺口 |
|---|---|---|
| 木屋前方木板 | `godot/scenes/components/solar_cabin/platform_board.tscn` 已独立引用 GLB；另有 coral、ochre 配色组件 | 目前是美术组件，没有建造实例ID、吸附边、占地或行走注册 |
| 小铺板 | `godot/scenes/components/solar_cabin/deck_tile.tscn` 也已存在 | 不能仅因名字是 tile 就认定尺寸与新网格匹配，需核对实际边界 |
| 当前太阳房平台装配 | `solar_cabin_front_platform.tscn` 由 `sunny_bloom_visual.gd` 读取实例表，结构件可转成 MultiMesh | 不能把渲染实例序号直接当玩家可建造对象ID，也不应复制整座平台上的家具 |
| 浅水种植台木面 | `cultivation_deck.tscn` / `.gd` 用13条 BoxMesh 组成约6.47×5.15米板面，厚0.10米 | 这是一整个固定木面，和木屋的独立彩色木板不同；脚本不提供行走区域 |
| 建造 | `construction_service.gd` 管固定 home_cabin、rooftop_planter、yokohama_station 的付费升级和施工 | 没有任意位置放置、占格、预览、拆除及动态物件快照 |
| 发布范围 | `play_scope.gd` 当前禁用 build | 需要单独开放家园扩建入口；不能用全开 `--full-world` 替代发布配置接入 |
| 种植摆件 | `farm_plot_single.tscn` 已有一格种植箱；`farm_plot.tscn` 为六格种植床 | 优先复用一格箱，不必每摆一件就生成六格 |
| 种植登记 | `FarmField.build()` 扫描 farm_plots，Farm 公开 register_plot | 目前是启动时全量登记；缺少完整动态增加/移除与事件接线接口 |
| 行走 | WalkArea 用矩形/多边形集合求路，Zone 收集 WalkAreas 的直接子节点 | 只新增模型或碰撞体不会自动允许角色走过去 |
| 船只避障 | Zone 当前从 Models 收集阻挡，WaterNavigation 缓存网格与空间索引 | 动态平台必须接入阻挡查询，并在变更后 invalidate |
| 存档 | 根快照当前v3；Farm快照v2；Farm.from_dict 只恢复已登记地格 | 需要布局快照和跨模块恢复顺序；只保存模型位置不足以恢复种植 |

场景现状另有文档偏差：主设计及农场条款仍有“太阳房与浅水共12格”的旧描述，而当前 `zone1_home_harbor.tscn` 使用一格 `farm_plot_single.tscn`，浅水仍为六格。后续实施应保留实际稳定ID，并同步条款，不按旧12格说明重建场景。本次未改既有格数与迁移行为。

## 3. 通用木板预制体建议

建议新增稳定玩法包装 `godot/scenes/buildables/wood_deck.tscn`（拟新增），引用现有木板美术，不改旧路径、不覆盖木屋实例。结构建议：

```text
WoodDeck                         玩法实例与组件定义引用
├─ Visual                        引用已有 platform_board.tscn
├─ SurfaceDefinition             顶面高度、承载多边形、可走轮廓
├─ SnapAnchors                   前/后/左/右连接边
├─ PlacementFootprint            建造占地与船只阻挡定义
└─ InteractionAnchors            可选施工操作点
```

上述节点/资源是建议契约，尚无实现。根坐标建议放在顶面中心，模型通过子节点偏移归一；根缩放保持1，尺寸和轮廓以实测为准。木板是建筑用的一块铺板/平台模块，不等同于背包里的木料。

板上摆件通过稳定 support_instance_id、局部位置和朝向关联承载板；是否挂成场景子节点属于表现选择。可变布局的权威数据放在服务里，不靠节点父子关系代替状态。首版一个种植箱只占一块板，暂不做跨板摆放。

木板种类、材质变体、成本、占地、支持类型写入建造目录；实例只存类型ID、稳定实例ID、位置与朝向。实例ID不随坐标、数组顺序或节点重命名变化。

现有候选 AssetID 为 `SEA-SCENE-SBR-PLATFORM-BOARD`；分账本由 `assets/registry/ledger_index.json` 路由到 scenes.json。当前源 manifest 的许可为 `pending_user_reference_rights_review`，复用时如实保留。玩法包装不重复注册同一份美术为新资产；若需要重新建模标准尺寸，则按项目资产流程另行派生和登记。

## 4. 需要增加或修改的模块

| 模块 | 修改建议与边界 |
|---|---|
| SEA-BUILD | 在 `godot/src/construction/` 增加独立布局服务、建造目录和放置控制器；布局服务唯一拥有实例及占用状态，现有 ConstructionService 继续管固定建筑升级 |
| SEA-INVENTORY | 复用注入支付端口；最终确认时重验位置和资源，成功只扣一次；预览和取消不扣料 |
| SEA-UI / INTERACT | 增加木板/种植箱选择、绿红预览、旋转、取消和连续放置；建造模式阻断底层水面航行、走路、播种输入 |
| SEA-WORLD / MOVE | 场景适配器把同高度的静态地面及新增板轮廓汇总到连通的可走区域，并提供增删后的查询更新；防止只给每块板独立WalkArea导致跨板路径失败 |
| SEA-NAV | 动态木板占地纳入水面阻挡；更新后清缓存，检查现有航线与泊位；不得封住当前船只或唯一上下船通道 |
| SEA-FARM | 增加增量注册/注销接口，稳定plot_id与摆件实例绑定；初始化空地、绑定Farm、接上操作气泡、成熟通知与笔记查询 |
| SEA-SAVE | 布局加入强校验快照，升级版本并迁移旧档为空动态布局；调整整份快照的候选世界验证与恢复顺序 |
| SEA-ASSET | 校验复用木板的实际尺寸、顶面、拼缝、颜色与阴影；维护资产引用关系，不批量刷新未知哈希 |

建议布局服务公开 `can_place`、`place`、`can_remove`、`remove`、`instances`、`to_dict/from_dict`，发出布局变更事件。以上为拟定接口；规则服务通过注入端口读取可建区域、库存与占用，不能重新直接访问 Main/Economy/UI。主场景只负责装配，不继续堆放规则。

## 5. 最容易遗漏的规则

1. **承载与通路分别校验。** 种植箱整个底面要在有效承载面内，且至少一侧保留角色能到达的操作位置；箱体占地应从可走面扣除，不能让角色穿箱。现有 approach_action 采用朝角色方向偏移1.35米，需要改成选择有效的操作锚点。
2. **不能只看单块木板的碰撞。** 航行代码使用独立水面形状查询；行走用自己的多边形算法。三维碰撞体不会自动更新这两条链路。
3. **地面高度不能全局写死。** 木屋和浅水平台当前顶面不同；首版应继承所连接平台高度。跨高度连接需后续单独设计过渡。
4. **新建箱子要完成全部接线。** Farm.register_plot 当前只追加规格，不做去重/事件发布；Main._setup_farm 只在初始遍历中启用气泡并连信号，动态实例不能漏掉。
5. **阻止破坏性拆板。** 板上有摆件、站着角色、属于泊位、或拆后切断家园通路时拒绝。首版可先不开放拆除/移动；若开放，非空种植箱必须保留作物或拒绝操作，不能静默清空。
6. **材料要有来源。** 当前默认循环主要是瓶盖、种子和农产品，打捞入口锁定。若扩建消耗木料，应同步给补给站加入木料供应或明确其他获取方式；不能开放按钮却让玩家永久缺料。具体成本本次不定数值。

## 6. 存档方案重点

建议布局快照独立于 Farm：木板记录 `instance_id/content_id/zone/position/rotation`；种植箱另有 `support_instance_id/local_position/rotation/plot_id`。Farm继续唯一保存作物种类、浇水、剩余生长日与收获次数，不在摆件里复制一份。

恢复分两步：

- **候选验证：** 根据整份存档布局构造只读的候选承载/行走/阻挡数据，验证重叠、支撑引用、重复ID、农田引用及玩家/船的位置。当前 validate_world_state 只查询已经存在的世界，会误拒绝“站在存档新平台上”的角色；因此仅改变模块恢复先后顺序不够。
- **统一应用：** 验证全通过后恢复布局 → 重建空间和种植登记 → 恢复Farm及其余状态 → 恢复角色/船 → 统一通知。期间不发中间业务事件、不扣建造费、不写中间档。失败必须保持当前世界和有效备份不变。

Farm.from_dict 会跳过未登记ID，所以动态箱必须在恢复Farm之前注册；同时检查 `_absorb_removed_cells` 的旧地格合并迁移，避免将动态ID误认成旧多格床子格。旧 home_plot / platform_plot 系列ID继续保留。

## 7. 推荐实施顺序和验收

1. 定下首版范围、木板尺寸、费用和材料来源；在主文档登记范围变化，把建议转为SEA-BUILD/SEA-FARM等稳定条款并逐条入账。
2. 做通用木板与单格种植箱玩法包装，验证顶面、拼接与承载，先让相连木板可走、船会绕行。
3. 实现预览/确认/扣费与动态箱登记；复用现有种植气泡，完成新增箱的三日生长和收获。
4. 实现布局快照、候选验证和旧档迁移，完成冷启动和热读档；再接入默认最小版本入口。

实施后的必要专项：正常放置、重叠/悬空/不连通拒绝、取消不扣料、重复点击不重复支付、占用泊位拒绝、跨板/L形走路、种植箱旁可操作、船绕平台、满包收获保留作物、07:00不重复生长/收货、站在新增板上存读档、破坏快照不污染现场、旧档仍可读。真实渲染另查板面接缝、水线、箱底贴合、角色不穿箱与读档后外观一致。

运行验证必须通过 `scripts/run_verification.py` 隔离用户存档。新增专项通过后再跑必要现有集成，日志和截图放工程外 sea-work。当前仅完成静态研究，未执行游戏或真实渲染验证。
