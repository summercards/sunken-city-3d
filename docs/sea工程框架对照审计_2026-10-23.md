# sea 工程框架对照审计与改造建议

日期：2026-10-23。范围：当前 sea 工作区的目录、正式运行代码、资产清单、文档、构建与验收入口；对照本机 ShellStorm2 现行工程契约。本文是审计与提案，不是已完成改造的声明。

> 目录归位提示（2026-10-24）：文中「根目录 22 个 JS / index.html / vendor」等描述对应审计当时的位置，这些文件现已迁入 `web/`，网页测试迁入 `web/tests/`。正文保留原快照，未回改。

## 1. 结论

**sea 已有模块化基础，但还没有达到“以主文档为中控，每个功能有独立文档和独立账本，并能独立交接与验收”的工程要求。** 当前更接近“网页版原型 + Godot 移植与原生扩展 + 局部组件化美术管线”。

用户于本次审计后明确了管理原则：**主文档 → 每个功能的独立文档 + 独立账本 → 对应实现、数据、资产与验收证据。** 本文按此修订。功能是文档与账本的管理单位；模块是代码组织单位，两者允许映射，但不能用一本模块总账替代多个功能各自的文档和账本。

应保留现有玩法、区块场景、数据表和资产，逐模块补治理和拆依赖。优先处理唯一事实源、可覆盖正式场景的构建工具、测试覆盖对象，再做大范围路径整理。仅把文件搬进新文件夹不能完成解耦。

这里的“独立管理”不等于每个模块零依赖或单独一个 Git 仓库，而是：依赖有声明；通过命令、查询、事件交接；状态有唯一写入者；可用替身独立测试；资产与内容可以追溯；最终有正式接入验收。

## 5. 关键证据与影响

### 5.1 Economy 已成为跨模块中心

`godot/scripts/economy.gd:21–24` 直接载入 Inventory、Farm、Orders；同文件含 SITES、FACILITIES、SHIP_RECIPE 及其业务状态。

- `godot/scripts/core/farm.gd:62–88` 通过 Economy 查询温室、船等级、建造等级，并以 `zone5` 判断解锁条件。
- `godot/scripts/core/orders.gd:69–78` 直接遍历 `Economy.site_levels` 和读取 `ship_level`；交付直接调用 `Economy.inventory.remove()`。
- `godot/scripts/hud.gd:445–456` 遍历 `farm.crops` 并直接设置 `farm.selected_crop`。

这不是说所有这些调用都会造成 bug，而是种植、订单、UI 的实现都知道别人的内部结构，难以单独换实现、模拟输入或交接开发。

目标：Inventory 管库存与交易；Construction 管建造与设施；Vessel 管船升级；Farming 管地格与种植；Orders 管订单。种植所需温室加成和解锁资格由查询端口提供，具体区块条件通过数据/装配传入。不要简单把 Economy 拆成更多全局单例。

### 5.2 Main 与存档、UI 双向了解内部实现

Main 除接线，还负责点击命令、行走、上船下船、航线、潜水切换、奖励提示、休息、自动存档和调试截图。

`godot/scripts/core/save_game.gd:161–184` 调用 `main._sync_zone_levels()`、`cam._apply()`、`hud._refresh()`，并清空 `main._walk_path`、修改 `_after_walk`；后续还直接重挂玩家节点。

建议将移动/靠泊协调、交互协调、表现反馈、存档协调、调试入口抽为有明确职责的对象。SaveService 只组织快照校验、迁移和写盘；模块各自拥有快照恢复逻辑，UI 从恢复完成事件重新查询状态。先校验所有必要快照，再提交恢复，避免半恢复；保留旧档迁移与相对冷却规则。

### 5.3 测试对象与正式实现不同

`godot/project.godot` 的正式 Economy 是 `res://scripts/economy.gd`；`godot/tests/test_core.gd:3–5` 载入 `res://src/core/economy.gd`、`zones.gd`、`sail_nav.gd`。

源码引用检查中，这三份旧核心脚本的精确资源路径出现在 test_core；`src/core/ground_path.gd` 则确实被正式 `walk_area.gd` 使用。因此不能把整个 src/core 当废弃目录，也不能把 parity 测试通过等同于正式经济模块通过。

`godot/tests/test_farming.gd:20–25` 则实例化整个主场景，再取得全局 Economy。它是有用的集成测试，但尚不满足种植模块的独立验收要求。

建议保留旧 parity 测试为迁移参考，明确标签；新增直接覆盖正式规则实现的单元/契约测试，逐步退出重复经济实现。现有正式接入测试继续保留。

### 5.4 已有资产组件，但尚未形成生产登记闭环

43 份组件清单已经包含 AssetID、几何指纹、材质角色、尺寸、母版位置等。抽查轿车清单还明确写了 `collision_owner=godot_wrapper_if_future_import`、`asset_ledger=null`。

这些组件应登记为其真实阶段，例如“制作源已有、运行接入待核验”，不能因有 Blend 就标记正式可用。也不能因为清单说未登记 ShellStorm2，就把 sea 资产写进 ShellStorm2 账本；sea 需要自己的登记入口。

当前清单和多份 Blender 工具写死本机绝对路径，还指向 outputs 中的历史制作源。迁移要用仓库相对路径、源索引和受控归档映射，并验证 Blender 外链；不能直接删除 outputs。

### 5.5 正式手工场景与生成器存在所有权冲突

`godot/tools/build_zones.py:119–123` 无条件生成区块、环境与主场景；`:235–236` 直接写 `scenes/main.tscn`。`build_zone_scenes.gd:22` 对模型区段明确注明手改会被覆盖。README 同时鼓励在编辑器里维护实际场景。

应区分：历史烘焙源、可再生中间层、正式手工场景。生成器默认输出候选目录与差异清单；正式场景只做受控更新。对确实允许重生成的子场景标注 generated 所有权，并用外层手工场景组合。初始化模式仅允许目标尚不存在，已有目标不得静默覆盖。

### 5.6 检查脚本和导出边界还不能统一兜底

`godot/verify.sh` 是 `/bin/sh + set -e`，将 Godot 输出管道给 tail/grep，管道结果可能不能反映 Godot 原始退出码；截图阶段又有 `|| true`。因此不能仅凭该脚本打印“验收完成”判断通过。

`verify_surface.sh`、`verify_farming.sh` 已使用 `set -euo pipefail`、日志扫描，surface 还精确排除了一个预期坏 JSON 诊断。这些实现可以复用，不必全部推倒。

`godot/export_presets.cfg` 是 `all_resources`、额外包含 `*.bin`、仅排除 `build/*`。本次只在 `.godot/` 发现 `.gdignore`，所以测试、工具、截图等目录需要补明确导入/发行边界；**实际是否入包及占用多少须另跑 PCK 审计**。根 art_source 在 Godot 根外，本身没有被当前 res:// 覆盖。

### 5.7 现行规则没有统一主源

`docs/功能重做计划.md:477–480` 描述订单有剩余时间、到期换单；`godot/README.md:126–129` 写长期有效；当前 `orders.gd:119–135` 只对已交付后的补位计时。

可确认文档彼此冲突、代码目前是长期订单；不能据此擅自裁定用户目标必须是哪一种。改造时先追溯已确认设计，冻结对应 FeatureID 契约，旧实现记录保留历史身份。

## 6. 目标模块划分（提案）

以下是代码模块划分建议。文档与账本另按主文档登记的每个功能独立建立：一个模块可以承载多个功能，但每个功能必须有自己的文档和账本，不按脚本数量划分功能。

| 模块 | 唯一拥有的状态/职责 | 从现有代码承接 | 对外接口示例 |
|---|---|---|---|
| session / bootstrap | 会话、模块装配和生命周期 | Main 的接线、GameState 的会话部分 | start_session / change_mode |
| player_navigation | 角色、船的移动/靠泊与输入协调 | Main 移动部分、boat、character、寻路 | move_to / board / disembark |
| world | 区块装载、布局与可行走区域 | Zones、zone_scene、WalkAreas | query_landing / load_zone |
| interaction_gathering | 焦点、操作进度、采集点冷却 | interactor、gather 系列 | interact / cancel / collected |
| inventory | 背包、仓库存量与交易原子性 | Inventory、Economy 部分 | query / try_exchange / changed |
| construction | 建造等级、施工进度、设施解锁 | Economy 建造部分、build 系列 | begin_upgrade / query_bonus |
| vessel_progression | 船升级、航行资格 | Economy 船等级与配方部分 | upgrade / query_capability |
| farming | 地格、日期推进、浇水与产出 | Farm、farm_plot/field | plant / water / harvest |
| salvage | 打捞过程、冷却与结果 | Salvage、winch、Main 部分 | start / tick / finish |
| diving | 氧气、潜水会话、宝箱发现与开启 | DiveAir、UnderwaterWorld | enter / search / exit |
| orders | 订单列表、交付、补位 | Orders、trade_board | fulfill / reroll / query_offers |
| save | 存档封装、模块快照协调与迁移 | SaveGame、自动存档部分 | collect / validate / restore |
| presentation_ui | HUD、菜单和操作反馈 | HUD、ui 系列 | 命令适配 + 只读视图 |
| rendering | 水面、海底着色、灯光与后处理 | water、uw、环境资源 | 只读状态与渲染参数 |

资产生产线另按场景/角色/道具/UI/VFX/音效/音乐组织；缺失的模块先登记 planned，不制造虚假的成品与验收状态。上述粒度可合并，例如早期船升级可作为 progression 子模块，关键是所有权与接口不丢失。

## 7. 主文档中控与每功能独立文档、独立账本

### A. 主文档是唯一管理中枢

建议在现有 `GDD_V1.0.md` 上升级管理结构，保留主文档入口，不再另造一份并行主设计。此处只修订改造方案，尚未改写 GDD。

主文档负责项目目标、核心循环、全局规则、功能范围与分组、功能依赖和交接关系、阶段安排，并用一张功能导航表直接指向每个功能文档及账本。README 和机器索引只能服务这一入口，不能替代主文档中控。

主文档中的每行至少包含：`FeatureID / 功能名 / 所属系统 / 目标摘要 / 依赖功能 / 独立文档链接 / 独立账本链接 / 当前状态摘要`。状态摘要从功能账本汇总，并保留来源与更新时间；详细实施状态只在该功能账本维护。

独立功能文档、账本都必须反向链接主文档的功能条目，跨功能依赖通过 FeatureID 指向对方文档。主文档规定的全局约束对各功能生效；功能文档维护本功能的完整细则，不在主文档重复整份细则。

### B. 每个功能有独立文档和独立账本

每个被主文档登记的功能，无论计划中、开发中或已实现，都有独立的 `功能文档.md` 和 `功能账本.md`，先采用容易阅读和审阅的 Markdown。若后续需要 XLSX 或 JSON，明确唯一编辑源，其他形式生成，不并行手工维护多份相同状态。

| 文件 | 必须回答的问题 | 内容 |
|---|---|---|
| 独立功能文档 | 这个功能应该如何工作，如何独立开发和验收？ | FeatureID、主文档入口、目的与边界、玩法/交互流程、输入输出、状态所有者、命令/查询/事件、依赖契约、数据与资产引用、失败/回滚、存档迁移、验收标准 |
| 独立功能账本 | 这个功能实际做到了哪里，证据在哪里？ | 稳定条目ID、对应设计条款、实现任务/交付项、状态、责任归属、代码/场景/配置/资产位置、验证基线与结果、问题和后续动作、变更记录链接 |

账本条目要覆盖功能文档的要求，明确“未开始、开发中、已实现待验证、已验收、受阻”等状态；没有证据不能标已验收。功能文档描述目标规则，账本描述实施事实，不能用代码现状反写目标设计。

例如主文档将“播种、浇水、生长、收获”分别登记为四个功能，则四者各有文档和账本，不能只交一份种植模块说明。如果它们被定义为一个功能的四个步骤，则先在主文档明确该粒度。功能拆分按可描述的行为、边界和验收结果确定，不默认一个按钮或一个函数就是一个功能。

工作顺序固定为：**从主文档定位功能 → 读取该功能文档和账本 → 核对依赖 → 实施与验证 → 更新功能账本及必要的功能设计 → 同步主文档导航、关系和状态摘要。** 新功能先在主文档登记，再建立独立文件；变更全局规则或跨功能交接时先同步主文档与受影响功能契约。

### C. 内容定义与调用登记

items/crops/orders 等配置继续各有唯一事实源。内容登记记录 `ContentID → Owner → 定义文件/条目 → AssetID → 使用模块 → 存档字段`；不把价格、产量、堆叠上限又手抄进功能账本和资产账本。

例如番茄物品定义由物品目录拥有；番茄作物的生长规则由 Farming 拥有；订单只引用 tomato 的 ContentID；番茄模型只在道具资产账本登记一次。玩家当局库存属于运行状态，不是工程管理账本。

### D. 资产分账本是功能账本的支撑

每个功能自己的账本必须能定位它使用的内容和资产；资产分账本负责生产信息，不能代替功能账本。共用资产由多个功能账本引用同一个 AssetID，不复制多份资产主记录。

在根 `assets/registry/` 建总索引和按生产域划分的账本；至少场景、角色、道具、UI，VFX/音效/音乐按实际生产启用。无需为没有的武器/敌人内容空造九本。

每个资产记录 AssetID、domain、制作状态、源母版、必要外链、导出/运行路径、Prefab、版本、哈希、授权、消费模块、验收证据。总索引只路由，不重复资产行；跨模块使用同一资产通过 ID 引用。

根账本路径按 repo:// 语义解析；Godot 内运行路径明确标为 res:// 或 godot 相对路径，避免两个根混淆。运行时只读取必要的轻量 JSON 投影，不读取制作账本或 XLSX。

## 9. 改造顺序与每阶段完成判据

### P0：建立可信基线，阻止继续扩大风险

1. 记录当前工作区与存档/资产基线，保留用户未提交改动；冻结现有正式资源路径。
2. 先确定现有 GDD 为主文档中控，梳理功能边界和稳定 FeatureID，建立逐功能导航；README、AGENTS 和规范入口指向主文档。标明正式 Economy、旧 parity 代码、网页烘焙链。
3. 保护正式 TSCN：生成器改候选输出/首次初始化，重生成前验证不会覆盖手工场景。
4. 统一验证入口：真实退出码、完整日志、明确预期故障、未执行项；Autoload 前隔离测试用户数据。

完成判据：每条正式入口可定位；测试故意失败时 runner 必须失败；重复生成不会改变手工场景；当前主要玩法和画面基线有可复查记录。

### P1：先落独立管理与账本

1. 从主文档登记的完整功能清单逐项建立独立功能文档和独立功能账本，包含计划中功能；补齐主文档的直接链接、依赖关系及反向链接。代码模块目录不替代功能清单。
2. 建资产总索引和所需分账本；先登记 43 个既有组件，再扩到现有 Godot GLB、材质、植物、UI 等资源。
3. 建 ContentID/AssetID/FeatureID 引用关系与当前源索引。
4. 分离现行设计、当前实现、开发历史；订单到期等冲突逐项记录来源和处理结果。

完成判据：主文档每个功能都有唯一 FeatureID、可访问的独立文档和独立账本，功能设计条款在本功能账本中有承接；所有独立功能文件均可追溯到主文档，无遗漏或游离功能；已实现功能有 Owner、入口和验收定位。AssetID 跨资产账本不重复，共用资产只登记一次。文件齐全与功能完成分别判定。

### P2：用种植模块做第一条完整拆分

1. 由装配层给 Farming 注入库存交易、设施加成、解锁资格、日期/时间端口。
2. Farming 不再访问 Economy 全局变量；UI 用 select_crop 等命令，不直接写内部状态。
3. 种植最小场景可运行；用替身测试缺种子、背包满、缺水、重试与读档。
4. 正式游戏仍使用同一 Farming 实现，原集成与真实表现回归保留。
5. 试点通过后以同一方式迁移 Orders、Construction、Vessel，Economy 逐步退为兼容入口并最终清理。

完成判据：Farming 独立测试不加载 main.tscn、整座城市或真实订单模块；改种植内部实现不需要改存档总调度或 Main 的内部字段访问；现有规则与旧档语义保持。

### P3：拆 Main、存档与表现依赖

建立移动/靠泊、交互、反馈、存档与调试的独立协调入口；各模块注册自己的快照处理器；UI 订阅视图更新。不要把所有调用变成无类型全局事件总线，必须保留事件所属模块、载荷结构与失败语义。

完成判据：存档模块不访问 Main/HUD 私有字段；失败恢复不会留下半提交状态；主场景脚本主要负责模块生命周期与接线，行数只作辅助观察。

### P4：统一资产管线、目录与发行边界

逐批归位运行数据和代码；保留必要兼容映射并清理已退出实现；把可复用 outputs 脚本先移到 tools、文档移到 docs，临时媒体归档到工程外；加入 Git LFS 策略但不擅自重写历史；调整导入/导出边界并实际审计 PCK。

完成判据：干净克隆能按文档启动和验证；Blender 外链有效；运行引用无断链；发行包仅含必要资源；资产替换无需改消费者代码路径。

## 10. 建议门禁清单

以下为拟新增或统一的能力，不是当前已存在的工具：

| 门禁 | 应检查的内容 |
|---|---|
| feature_documentation | 主文档功能条目与独立文档、独立账本一一对应；双向链接有效；设计条款有账本承接；状态摘要与来源一致 |
| module_registry | 功能到代码模块的映射、唯一 ID、Owner、路径、接口/测试/记录引用完整 |
| module_dependencies | 禁止业务模块回调 Main/HUD 内部字段；白名单依赖；检查循环；动态调用另做语义审查 |
| content_contracts | ContentID 唯一、schema、外键、AssetID 和存档引用 |
| asset_registry | AssetID 唯一归属、路径/阶段/版本/哈希/授权、总索引一致 |
| source_runtime_boundary | 制作源不能被运行代码读取，必要投影可重建与验证 |
| authored_scene_protection | 构建重复执行不覆盖正式手工场景；候选差异可审阅 |
| verification_runner | 退出码、完整日志、精确预期错误、隔离用户数据、测试分类 |
| export_audit | 真正导出 PCK 检查资源集合；Git ignore 不作为不入包证据 |

纯路径扫描无法证明所有权和失败语义正确；结构门禁必须配合模块契约、专项测试及正式流程回归。
