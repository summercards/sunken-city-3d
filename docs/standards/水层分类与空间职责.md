# 海上主场景建筑两类与空间职责

[主文档](../../GDD_V1.0.md#feature-control) · [建筑分类入口](../../assets/registry/BUILDING_CLASSES.md) · [资产登记](../features/asset/spec.md) · [世界装配](../features/world/spec.md)

2026-11-02按用户最新要求修订。此规则覆盖此前以五种water_layer值充当建筑分类的说法；旧开发记录保留为历史证据。

**范围仅限海上主场景及其制作候选。** 本文“水下”是海面场景里可见的基座与观赏建筑，不指独立海底／潜水玩法场景。`godot/scenes/underwater/` 及其资产另外处理；未确认海上归属的43项ENV-TOWER-DISTRICT独立参考组件也排除。

## 1. 建筑只有两类

正式分类字段为场景分账本的 **`building_class`**：

| 类别 | 字段值 | 职责 |
|---|---|---|
| 水上功能建筑 | `above_water` | 承接玩家活动空间、行走面、泊位、角色／船只阻挡，以及已定义的交互和生产功能 |
| 水下观赏建筑（含海下基座） | `underwater` | 只提供外观；不承担阻挡、通行、交互、生产或任何玩法功能 |

船、独立植物、生活摆件、色板和混合总览不是建筑分类对象；海底场景与范围外参考件也不纳入本次分类，字段为JSON `null`；null不是第三类建筑。与建筑成套维护的基座、柱脚、支撑底框和水下装饰推进舱按两类职责登记，不能因为在同一模型包里就继承上层的玩法职责。

整栋阳光房的设施总成归水上，独立海下基座及其全部构件归水下。父总成、子件和源版本不是同一种计数单位；水下子件可以隶属水上总成，无须与父级同类。

两类建筑共用[场景Skill](../../.agents/skills/sea-scene-component-authoring/SKILL.md)的一位小数风格数据（尺寸、比例、倒角、色板、PaletteUV和材质角色）；制作先按building_class分类，再加载水上／水下差异。水线、摆位及空间／功能职责按各类附件，水下不另用一套风格尺度。

## 2. 允许和禁止的内容

| 内容 | 水上功能建筑 | 水下观赏建筑／基座 |
|---|---|---|
| 行走面、站立点、泊位 | 由设施按功能提供；墙、梁等单件不必各带行走面 | 禁止；即使视觉顶板接近水面也不能用来登陆或站立 |
| 角色碰撞／阻挡 | 按可见墙体、边缘与功能需要提供 | 禁止CollisionObject3D及任何角色阻挡代理 |
| 船只／航线阻挡 | 设施按海面活动范围提供；仅由水上部分派生 | 禁止BlockerSet有效形状、water_shapes、导航障碍及隐形阻挡 |
| 点击、E键、业务交互 | 按所属功能契约接入 | 禁止交互点、动作入口、资源产出、升级／收获／仓储等功能 |
| 存档与状态 | 由对应功能唯一写入 | 不新增玩法状态或存档字段；资产身份及静态摆放记录不属于玩法功能 |
| 岸线／吃水泡沫源 | 按水上接触轮廓与设施专项生成 | 禁止从水下基座或观赏楼生成岸线／泡沫种子 |
| 颜色、材质、纯视觉动画 | 允许 | 允许；只读环境时间驱动的表现不产生业务状态 |

水下主体应在水面以下；基座顶板与水上板底的视觉接合不授予任何空间或功能资格。已存源跨越水线时，应明确水上活动面与水下视觉段，不能只改分类就宣称模型已完成分段或水线验收。水上总成也不得扫描水下子树去派生行走、碰撞、阻挡或岸线。

围网、浮舱、推进器的**模型**可以在水下只作装饰。渔场禁航区、船只避让等业务形状由水上渔场服务拥有，不能归到水下模型上。“模型在水下”与“水上设施管理这片水面”分开登记。

## 3. 账本和入口

主记录仍只在 `assets/registry/ledgers/scenes.json`，由ledger_index.json路由；每项新增building_class，AssetID、源路径、授权、哈希和原制作阶段保留。

两类入口是按AssetID生成的只读视图，不建立第二份可编辑主记录：

- [水上功能建筑登记](../../assets/registry/views/buildings_above_water.json)
- [水下观赏建筑／基座登记](../../assets/registry/views/buildings_underwater.json)

`water_layer` / `water_layer_role`保留为既有场景及工具的装配描述。`surface`、`amphibious`表示原空间装配方式；`backdrop`表示远景显示用途；这些值**不再作为建筑职责分类**。独立字段building_class只有above_water／underwater，检查器不接受第三种职责类。混合总览不作单栋统计；远景沉没建筑按水下观赏职责登记，实际标高仍待逐实例核验，不能因旧backdrop值而豁免无功能规则。

原category／classification继续描述生产类型（墙、设施、植物等），不决定该物体能否提供玩法。登记“水上”也不自动开启尚在规划的功能。

## 4. 唯一写入与校验

`tools/apply_water_layer.py`维护家族规则、明确的海下基座／视觉组件例外、building_class及两个派生视图；新增家族未登记即失败。规则已把独立太阳能花屋总成恢复entity，把BLB基座的兼容角色对齐正式TSCN的part，不改AssetID。

静态门禁检查：两类取值、567行字段完整性、家族一致性、两视图不重不漏，以及水下登记不得声明碰撞、行走、阻挡、交互、资源或玩法状态。视图仅含AssetID，不能复制编辑源、路径、授权与哈希。

```text
python tools/apply_water_layer.py
python tools/apply_water_layer.py --dry-run
python scripts/check_feature_contracts.py --sync
python scripts/check_feature_contracts.py
```

## 5. 登记完成与运行验收分别记录

本次完成文档／账本整理及静态检查口径，未修改Blender源、模型、Godot业务代码或正式场景摆位。新职责是目标契约，不能将既有stage或旧water-layer全绿当成这份新契约已经全面运行验收。

后续运行验收必须通过scripts/run_verification.py隔离用户数据，分别核对：水上活动面／泊位／几何一致；水下所有子件无碰撞、阻挡、交互、功能和岸线；新建筑漏声明拒绝；复合设施派生排除水下子树。旧water-layer存在未声明节点跳过、属性遮住metadata等缺口，见[清点审计](../development/2026-11-02_surface_building_inventory_audit.md)，需修复后才能签完整运行验收。浮店位置／靠泊故障继续保持pending。

潜水玩法区的宝箱、地形不属于本次“海上场景中的水下观赏建筑”；它们仍由独立玩法契约管理，不能改登记为观赏楼以关闭已有玩法。
